03Machine-readable interface

Every file below sits beside this page and is regenerated on the same schedule. They are static, cacheable, and require no key.

Machine-readable files published alongside this page
FileContents
status.jsonCurrent state of every public component with 90 day uptime. The canonical resource. Validates against schema.json.
status.txtThe same reading as plain text. The first line is a single token: OPERATIONAL, DEGRADED, PARTIAL_OUTAGE, MAJOR_OUTAGE or UNKNOWN.

Examples

# is the store up right now
curl -s https://healthymeats.github.io/shipley-status/status.txt | head -1

# one component, with jq
curl -s https://healthymeats.github.io/shipley-status/status.json \
  | jq -r '.components[] | select(.id=="cart") | .status'

# fail a deploy gate when anything is not operational
test "$(curl -s https://healthymeats.github.io/shipley-status/status.json | jq '.status.severity')" -eq 0

Check stale before anything else

When stale is true the probe has missed several runs, every component reports unknown, and the file is evidence of nothing except that nobody is measuring. It is not evidence the store is up and it is not evidence the store is down.

Match on id, never on name

Component ids are stable and will not change without a version bump. Display names get reworded.

Branch on severity

0 operational, 1 unknown, 2 degraded, 3 partial outage, 4 major outage. The severity integer is the field designed to be compared.

Uptime counts checks, not minutes

Days with no checks are excluded from the denominator. In uptime.json a null component means no checks ran that day: it is neither zero nor full.

Polling etiquette

Poll no more than once a minute. These files are static and regenerate every few minutes, so anything faster only costs bandwidth. Honour caching headers.

Reading is welcome, checkout is not automated

Reading status needs no permission or key. Checkout is a different matter and is covered at https://shipleyfarmsbeef.com/agents.md. If you are helping someone shop, build the cart and hand your buyer a link to approve and pay. Do not automate payment.

Building on our data

This status feed is not the only thing we publish. Our full product catalog is public too, and we take contributions: what we publish and why, catalog.json, and our integrations repository. Never sent a pull request before? Start here.

Please use the catalog file rather than crawling the site. Automated scanning and load testing are not welcome.

Corrections and requests

Something wrong with this data, or a component you wish were covered: beef@shipleyfarmsbeef.com

04Measurement method

What is measured

Every 30 minutes an unauthenticated HTTP GET is sent to each component above from a machine outside the hosting platform, and the response code, body size and elapsed time are recorded. Nothing on this board is self-reported by the site being measured, so a green reading is independent evidence rather than a claim.

How a state is decided

Operational is a 2xx or 3xx response in under 4000 ms. Degraded is a slow response, an HTTP 429, an HTTP 401 or 403, or a 200 carrying a suspiciously small body. Outage is a 5xx, a timeout, or a connection failure. A response that arrives but takes longer than 12000 ms is recorded as an outage on the grounds that nobody waits that long.

How uptime is counted

Uptime counts checks, not minutes. Days on which no check ran are excluded from the denominator rather than assumed healthy, and are drawn as hatched bars. A check that never ran is never counted as a passing one. This history covers 1 of 90 days and 40 checks so far.

What a green board does not prove

Every check is unauthenticated and read-only, so nothing behind a sign-in is measured. Checkout, payment capture, the register and order placement all require a session. Green means the storefront is serving pages, not that a card will clear.

How page changes are detected

Each page's HTML is hashed every run, after normalising the parts that differ on every request: Frappe emits a fresh random element id for each nav dropdown, so a raw hash would report every page as edited every few minutes. When a normalised hash moves the page really changed, and a CONTENT marker is recorded. Deploys are detected the same way, from the asset manifest.

Change markers

Lines marked DEPLOY, CONFIG, DATA or CONTENT are changes recorded by hand on the same timeline as incidents, so a fault can be read against what was changed just before it. They are not faults and never affect any percentage on this page.

When the probe stops

If the newest check is older than three intervals the board says so at the top, reports every component as Unknown, and states plainly that nothing on the page is evidence the site is up. A stale board is never a green board.
